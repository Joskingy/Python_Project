## The first question is context

Which branch failed? What changed in its configuration? Which account am I actually investigating? Answering an operational question can mean moving between several screens before the evidence comes together.

I built **amplify-ops** within BotoToolkit to make that investigation explicit. The tool checks identity, keeps resource scope visible, and distinguishes incomplete reads from complete results.

## Decisions that shape the tool

### Identity comes first

The operator supplies a profile, an expected AWS account, and selected regions. Checking identity before operational reads helps catch work in the wrong environment.

### Scope stays visible

Amplify Hosting inventory does not claim to discover every backend dependency. Reports explain what was actually read, with contextual errors and meaningful exit codes for partial results.

### Useful differences, withheld values

Configuration comparison surfaces changes while keeping the values themselves out of the report. The deployment command submits an explicitly reviewed retry, separate from the read-only commands.

## Scope and limitations

This case study covers an independent tool for Amplify Hosting operations in selected accounts and regions. CI authentication support is documented as future work. No uptime or productivity improvements are claimed here.

## The principle carries into delivery

BotoToolkit verifies a local operator’s identity. This portfolio’s delivery pipeline uses a separate mechanism, GitHub OIDC, to establish a workflow’s AWS identity. Both make the boundary between identity and permission explicit.
