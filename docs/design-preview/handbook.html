GitHub Actions to AWS, without stored keys.

Make workflow identity specific, deployment permissions narrow, and infrastructure changes reviewable.

The practice

Use a short-lived AWS role session for each authorized workflow. Scope who can assume the role separately from what that role may do.

The context

This portfolio publishes static files to a private S3 bucket behind CloudFront. Content updates and infrastructure changes have different consequences, so they follow different paths through GitHub Actions.

GitHub workflow→OIDC token→AWS role session

GitHub’s OIDC token lets AWS verify the workflow’s identity. The role’s trust policy defines which identities may assume it. The role’s permissions define what the resulting session can access.

Be precise about workflow identity

For the publisher, the trust condition names this repository and its protected production environment. The environment’s deployment branch policy restricts releases to main.

This excerpt is only the condition, not a complete role. The deployed template also defines the federated provider, allowed assume-role action, and the publisher’s permissions boundary.

Environment trust and branch restrictions work together.

An environment-based subject identifies the environment. The main-only deployment rule belongs to GitHub’s environment protection settings.

Separate routine delivery from infrastructure

The publishing role uploads site files and requests CloudFront invalidation. Infrastructure planning and application use separate roles and a manual workflow with change-set review and environment approval.

  • Publishing consumes the tested site artifact.
  • Planning prepares an infrastructure change set for inspection.
  • Applying executes the reviewed change set after approval.

OIDC removes the need for stored AWS access keys in the workflow. It does not replace least-privilege permissions, protected environments, or review of the code being executed.

Verify the boundaries

  1. Inspect the role’s trust policy and confirm the repository, audience, and environment match the intended workflow.
  2. Check that the production environment limits deployment to main, and that infrastructure application requires approval.
  3. Review publishing permissions against the actual site bucket and distribution.
  4. Inspect the change-set summary before applying infrastructure changes.
  5. After publication, check the public pages, assets, and HTTPS response.

These are review steps for this setup. A separate test environment is the right place to exercise denied-access scenarios without interrupting publishing.
